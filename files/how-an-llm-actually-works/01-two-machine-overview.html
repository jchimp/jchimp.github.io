System Schematic · rev. for the curious

Two machines, not one

An LLM product is two near-separate systems: one builds the model (offline, slow), one runs it (online, per message). The diagram reads top → bottom.

Zone A · Model production

Runs over weeks–months. Happens once per model version. Output: a frozen file of weights.

A1

Training corpus

A deliberately curated, filtered, deduplicated pile of text/code/data. Assembled by a separate process — not a live feed of user chats.

A2

Pretraining loop

Predict-the-next-token, billions of steps, across TPU / Trainium / GPU clusters (JAX → XLA). This is where most "knowledge" gets pressed into the weights.

A3

Base model — raw weights

A giant tensor of parameters. Fluent in patterns, but not yet a helpful, safe assistant.

A4

Post-training

Supervised fine-tuning on demonstrations + reinforcement learning from human/AI feedback (Constitutional AI). Adjusts the weights again to shape behavior, helpfulness, and safety.

A5

Evals & safety testing

Benchmarks, red-teaming, release gates. Pass → ship. Fail → back to the loop.

A6

Frozen checkpoint

The shipped model — a specific version (e.g. an Opus / Sonnet / Haiku release). From here, the weights do not change.

⎯⎯ Deploy · the frozen seam ⎯⎯

Weights are copied onto the inference fleet and locked.

Everything below this line only reads the weights. It never writes them.

Zone B · Serving

Runs on every single message, in milliseconds. This is the part your single-machine mental model already nails — it's just distributed and scaled.

B1

Client — web / app / API

You send a message.

B2

Backend / API gateway

Auth, routing, rate limiting — picks a server with the weights loaded.

B3

Context assembly

The exact prompt fed to the model is built here: system prompt + tool definitions + this chat's history (read from the DB) + your new message. This is the "custom logic controlling the conversation" you pictured.

B4

Tokenizer

Text → integer token IDs. The model's internal embedding layer (part of the weights) turns those IDs into vectors. This is the "embedding" inside the model — distinct from a side vector database.

B5 → B6

Forward pass → sample → repeat

One pass through the frozen weights yields a probability distribution over the next token. Pick one, append it, run again. Autoregressive — once per token, streamed out as it goes.

↻ loop — B5↔B6 repeats for every token in the reply, then stops at an end signal.
B7

Tool-call branch

If the model emits a tool call, an orchestration layer outside the model runs the tool (search, code, etc.), injects the result back into the context (→ B3), and generation continues. The model decides; the harness acts. Per session, not baked into weights.

B8

Response → UI → store

Streamed back to you, then written to the conversation DB so the next message can re-read it at B3.

The databases off to the side

Conversation history DB

Per account. Yes, your chats are stored — so the product can show them and rebuild context at B3. Storage for the product, not a wire into training.

Tool / orchestration layer

Per session. Manages the B7 tool loop, holds tool definitions, executes calls. Plain backend code — not part of the model.

Retrieval / memory store

Optional. Some features add a vector DB (external embeddings) for lookup. Separate from the model's own internal embedding layer at B4.

↥ The one loop that surprises people — and how it really runs

It feels like chatting should teach the model. It doesn't — not the one answering you. Conversation data can eventually inform a future training run, but only through a deliberate, curated, human-governed offline process that feeds back to A1 — never to the live weights.

Nothing you type edits the model replying to you. The reply is a read-only pass over a frozen file.

Zone A clockweeks–months · writes weights · produces one frozen artifact per version
Zone B clockmilliseconds · reads weights · runs millions of times a day, unchanged

Hardware (Trainium / TPU / GPU, JAX) is documented. The exact serving-code internals are not public — boxes B2–B8 are the shape of the system, not a leaked architecture.
