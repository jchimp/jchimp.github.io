Schematic · close-up of B5 + B7

Two loops, one stateless function

The model is a pure function: tokens in → one token out. Everything that feels like "an agent" is a loop the harness wraps around it.

Outer loop · the harness (agency lives here)
↻ build context → call model → did it ask for a tool? → run it → inject result → repeat
Inner loop · generate() (one model call)
↻ forward pass → sample 1 token → append → forward pass → … → STOP
runs once per token in a single reply
each outer turn runs the entire inner loop once
B5 · B6 Inner loop — the forward pass

One call to generate(). The weights are read-only the whole time. The only trick is the KV cache: process the whole prompt once ("prefill"), then feed just the new token each step ("decode") and reuse what's cached — that's why there's a pause, then streaming.

def generate(token_ids): # token_ids = ENTIRE context so far kv_cache = [] # per-call speedup, thrown away after out = [] # PREFILL: one big pass over the whole prompt logits, kv_cache = model.forward(token_ids, kv_cache) while True: next_id = sample(logits) # temp / top-p pick one token if next_id == STOP: break out.append(next_id) stream(next_id) # <- this is the "typing" you see # DECODE: feed ONLY the new token, reuse the cache logits, kv_cache = model.forward([next_id], kv_cache) return out

Inside each model.forward: the token IDs hit the embedding layer (weights), then every transformer layer does attention (each token reads every earlier token) + an MLP, ending in a probability over the whole vocabulary. No state survives the call — the model has already forgotten this turn.

B7 Outer loop — the tool harness

This is the "bolting on more than chat" part. Plain backend code. The model never runs a tool — it emits a structured request, the harness executes it, and "injecting" the result just means appending a message and calling the model again.

messages = [system_prompt, user_msg] # <- this list IS the memory while True: prompt = tokenize(render(messages, tool_defs)) reply = generate(prompt) # the entire inner loop runs here turn = parse(reply) if turn.tool_call: # model asked for a tool result = run_tool(turn.name, turn.args) # search() / exec() ... messages.append(turn) # record the request messages.append(tool_msg(result)) # INJECT the result continue # <- call the model AGAIN else: messages.append(turn) return turn.text # final answer, loop ends

The model "reads" the tool result with no special channel — it's just more tokens in messages on the next pass. The harness re-renders the whole growing list each turn (prefix-cached so it isn't wasteful). The model is stateless; the messages list is the entire state of the conversation.

The punchline for a programmer

There's barely any magic. A stateless tokens→token function sits inside a while-loop that detects a structured request, runs ordinary code, appends the output, and calls the function again.

Every "agentic" capability — search, code execution, file editing, multi-step planning — is the same loop with a bigger tool list. The model supplies judgment about what to call; the harness supplies the doing and the memory.

You could write the outer loop in an afternoon (you basically have, in your FastAPI projects). The hard part isn't the loop — it's the frozen file it calls.
